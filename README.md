Retail Sales Analytics

Анализ розничных продаж на Python и SQL

1. Цель и задачи проекта

Цель проекта - исследовать транзакционные данные интернет-магазина, изучить качество исходных данных, рассчитать выручку и определить особенности продаж по месяцам, странам и товарам.

Для достижения цели были поставлены следующие задачи:
  1. Изучить структуру и основные характеристики датасета.
  2. Проверить пропуски, полные дубликаты и нестандартные значения.
  3. Определить правила обработки дубликатов, отмен и операций с необычными ценами.
  4. Рассчитать выручку по операциям, отнесённым к обычным продажам.
  5. Исследовать помесячную динамику и распределение выручки по странам.
  6. Определить товары с наибольшей выручкой и количеством продаж.
  7. Сопоставить результаты Python-анализа с расчётами в PostgreSQL.

2. Данные и инструменты

В работе использован набор данных Online Retail из UCI Machine Learning Repository. Он содержит сведения о транзакциях интернет-магазина за период с 1 декабря 2010 года по 9 декабря 2011 года.

Исходный датасет включает 541 909 строк и 8 столбцов: `InvoiceNo`, `StockCode`, `Description`, `Quantity`, `InvoiceDate`, `UnitPrice`, `CustomerID` и `Country`.

Инструменты проекта: Python, Pandas, JupyterLab, PostgreSQL, DBeaver, Matplotlib, SQLAlchemy, GitHub.
Источник данных: [UCI Machine Learning Repository](https://archive.ics.uci.edu/dataset/352/online+retail)

4. Подготовка данных и правила расчёта

Для дальнейшего анализа была создана копия исходного набора. Полные дубликаты удалены с помощью `drop_duplicates()`, при этом остальные строки с пропусками сохранены, если могли быть полезны для расчётов.

Полные дубликаты: удалить (чтобы снизить риск двойного учёта).

Пропуски Description: сохранить строки (код товара и числовые поля пригодны для анализа).

Пропуски CustomerID: сохранить строки (не требуется для расчёта общей выручки).

Отрицательное Quantity: не смешивать с обычными продажами (отмены, возвраты).

Отрицательный UnitPrice: исключить из выборки обычных продаж (бухгалтерские корректировки).

Фильтр обычных продаж: InvoiceNo не начинается с C; Quantity > 0; UnitPrice > 0.

После удаления дубликатов размер очищенного набора составил 536 641 строку и 8 исходных столбцов. В дальнейшем был рассчитан показатель `Revenue = Quantity × UnitPrice`.

Выборка обычных продаж после применения фильтров содержала 524 878 строк. Общая выручка этой выборки составила 10 642 110,804 в единицах валюты исходного набора; валюта в использованных столбцах отдельно не обозначена, поэтому в отчёте сумма приводится без символа валюты.

7. Анализ товарных позиций

Первоначальный рейтинг по `StockCode` включал не только обычные товары, но и служебные позиции: `DOT`, `POST` и `M`. Для более содержательного рейтинга товаров эти три кода были исключены из отдельной выборки. В результате рейтинг лучше отражает товарные позиции, а не почтовые и ручные корректировки. 

Примечание: для товара 85123A применено правило группировки строго по коду, поэтому итоговая сумма учитывает все варианты написания описания

8. Отмены, возвраты и нестандартные операции
9. 
Счета, начинающиеся с C: 9 251 строка (сумма Revenue: -893 979,73).

Отрицательное Quantity без C: 1 336 строк (сумма Revenue: 0,00, так как цена равна нулю).

Отрицательный UnitPrice: 2 строки (сумма Revenue: -22 124,12, Adjust bad debt).

Отрицательные количества нельзя автоматически считать обычными продажами. Отдельное исследование таких строк помогает не смешивать продажи, отмены, возвраты и бухгалтерские корректировки. При этом по одним лишь доступным полям нельзя окончательно установить экономический смысл каждой необычной операции.

9. Проверка результатов с помощью SQL

Во втором ноутбуке данные были проанализированы в PostgreSQL. SQL-запросы рассчитывали сумму выручки по месяцам, странам и кодам товаров. Для результатов были построены графики с помощью Matplotlib.

Сверка результатов показала полное совпадение агрегатов: общая выручка в Python составила 10 642 110,804, и точно такая же сумма была получена при выполнении SQL-запроса `SELECT SUM("Revenue") FROM sales`. Месячные суммы и рейтинги также совпали. Это служит проверкой корректности группировок и агрегирования.

Для рейтинга товаров в SQL также исключались коды `DOT`, `POST` и `M`. При проверке товарного кода 85123A было зафиксировано решение группировать данные по `StockCode`, а не только по сочетанию кода и описания.

10. Ограничения анализа

  1. В данных отсутствует примерно четверть `CustomerID`, поэтому анализ поведения конкретных клиентов ограничен.
  2. Данные охватывают период с декабря 2010 года по 9 декабря 2011 года; декабрь 2011 года неполный.
  3. Назначение всех отрицательных количеств не подтверждено, поэтому их интерпретация требует осторожности.
  4. Для товарного рейтинга исключены служебные коды `DOT`, `POST` и `M`.
  5. Валюта не обозначена в используемых столбцах, поэтому суммы в отчёте приведены без валютного символа.
  6. Выводы описывают представленный датасет и не объясняют причин изменений продаж без дополнительной информации о бизнесе.

11. Заключение

В ходе проекта была проведена первичная проверка данных Online Retail, выявлены пропуски, дубликаты и нестандартные операции, подготовлена очищенная таблица и сформирована выборка обычных продаж. Рассчитанная выручка этой выборки составила 10 642 110,804.

Анализ показал, что максимальная месячная выручка в наблюдаемом периоде пришлась на ноябрь 2011 года, а Великобритания занимает первое место по сумме продаж среди стран. В товарном рейтинге после исключения служебных позиций лидируют коды 22423 и 23843. Результаты агрегирования были дополнительно проверены с помощью PostgreSQL.

Практические рекомендации: бизнесу стоит сфокусировать маркетинговые усилия и закупки на подготовке к осенне-зимнему сезону (пик спроса приходится на сентябрь–ноябрь). Также рекомендуется продолжать развивать клиентскую базу в Великобритании, параллельно исследуя потенциал роста в Нидерландах и Ирландии, которые занимают второе и третье места по выручке.

В результате проект демонстрирует полный базовый аналитический процесс: изучение данных, обоснование правил обработки, расчёт показателей, визуализацию и сверку результатов между Python и SQL.
